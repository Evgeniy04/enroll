## 3. Доменная модель прототипа

**[Факт]** Типы из кода:

```ts
Service  = { id; name; duration /*мин*/; breakAfter /*мин*/ }       // цены нет
Template = { id; name; slots: ScheduleSlot[] }
ScheduleSlot = { id; serviceId; startTime: {hours, minutes}; count } // N сеансов подряд
BookingLimit = { mode: 'days-ahead'|'specific-date'|'unlimited'; daysAhead; endDate? }
Event (календарь) = { id; title /*имя клиента*/; start; end; color } // статуса нет
User (мок) = { id; image?; username?; phoneNumber?; firstName; lastName; about }
```

**[Факт]** Правила `utils/schedule.ts`:
- конец блока = начало + (длительность + перерыв) × количество;
- перерыв после последнего сеанса тоже учитывается;
- переход через полночь не обрабатывается, возможен результат «25:30»;
- пересечения блоков не проверяются.

**[Факт]** Удалённая схема (коммит `4d187b1`, удалена в `6cf400d`):
- `specialist(userId, activityTypeId, isActive)` с уникальностью «один активный профиль на пользователя» и «один профиль на вид деятельности»;
- `activity_type(slug)`;
- `driving_instructor_profile(address, addressNote, about, drivingExperienceStart, workExperienceStart)`.

**[Вывод]** Автор планировал платформу с видами деятельности и отраслевыми профилями, начиная с инструкторов по вождению, но упростил модель. В целевой модели ([15](15-data-model.md)) отраслевые атрибуты не нужны в MVP: профиль специалиста универсален, а «профессия» — свободное поле. Специализированные поля, например стаж вождения, — кандидат для расширения через `profile_attributes` (jsonb) позже.

## 4. Аутентификация и доступ

**[Факт]**
- Better Auth с email OTP. Письма уходят через nodemailer и Gmail SMTP, без `await`, поэтому ошибки отправки только логируются.
- Ограничения частоты: отправка кода — 2 раза в 60 с, вход — 5 раз в 60 с.
- Плагин `phoneNumber` подключён, но `sendOTP` — заглушка с `console.log(phoneNumber, code)`, то есть **код попадает в лог сервера**.
- Cookies: `sameSite: "none", secure: true`. CORS разрешает только `GET` и `POST`.
- `trustedOrigins` включают `enroll://` и `exp://` в разработке.
- Ролей и разграничения доступа к доменным данным нет, потому что нет и самих данных.

**[Вывод]** Для web `sameSite: none` избыточен и повышает поверхность CSRF. При одном домене нужен `Lax` ([17](17-security-and-compliance.md)). Логирование OTP недопустимо в production.

## 5. UI, дизайн-токены, стиль

**[Факт]**
- Палитра — нейтральная shadcn: HSL-переменные, `--radius: 0.625rem`.
- Акценты — градиенты Tailwind (blue→cyan, purple→pink, emerald, orange) на иконках приветствия и OTP, `text-cyan-500`.
- Календарь — `react-native-big-calendar` с основным цветом `#6185d0`.
- Собственных шрифтов нет, используется системный.
- Переменная `--destructive-foreground` используется в `tailwind.config.js`, но не определена.

**[Вывод]** Визуальной идентичности как таковой нет, это стандартная тема shadcn. Сохранять из неё стоит:
- аккуратную плотность форм;
- пресеты длительности (30/60/90) и перерыва (15/30/45);
- подсказки под полями («Подготовка перед следующим клиентом»);
- «дружелюбные» тосты («Ночь, улица, фонарь… тёмный режим включён»).

## 6. Видео: восстановленные сценарии

**[Факт]** По кадрам видео:
1. Ввод email, «Продолжить», письмо с кодом, экран «Проверьте почту» с вставкой кода и таймером повтора, вход.
2. Главная — пустой календарь «Сентябрь 2026»: переключение «день / 3 дня / неделя», «сегодня», колокольчик без действия.
3. Контакты — карточки с телефоном и кнопкой звонка. Профиль специалиста: описание, «Позвонить», календарь с переключением вида.
4. Нажатие «Позвонить» открывает системную звонилку. **[Вывод]** В прототипе запись фактически всё ещё идёт через звонок.
5. «Мой профиль» — форма и переключатель темы.
6. «Параметры работы», вкладка «Услуги»: модалка «Редактировать услугу» со степперами и пресетами.
7. «Шаблоны дня»: раскрытие шаблона, редактор слотов (услуга, время начала через барабан, количество), «Список услуг в расписании: 13:00–17:00, Стрижка · 8 × (30 мин)».
8. «Расписание»: «График работы», «Ограничение записи» (на 30 дней, до даты, без ограничения), «Инструменты заполнения» (Периоды, Недели, Смены, Сброс), неделя с выбором шаблона по дням, бейдж «Сегодня».
9. Смена аватара: «Сделать фото / Выбрать из галереи», круговое кадрирование.

## 7. Диаграмма действий

**[Факт]** Диаграмма описывает:
- **Вход:** «Пользователь зарегистрирован?» → Регистрация или Авторизация → Проверка данных → «Данные корректны?» (нет — «Сообщить об ошибке» и повтор) → «Главный экран и календарь».
- **Цикл:** «Продолжить работу?» — Да → «Выбрать раздел», Нет → завершение.
- **Главный экран:** «Просмотреть текущие записи» → «Выбрать действие»: Просмотр, Редактирование (изменить и сохранить) или Отмена (подтвердить и отменить).
- **Контакты:** список → специалист → профиль → «Выбрать услугу и доступное время» → «Создать запись на приём» → «Подтвердить запись».
- **Настройки:** «Открыть параметры работы специалиста» → «Выбрать настройки»:
  - управление услугами;
  - настройка типов рабочих дней («Стандартный, интенсивный или короткий день», «Редактировать или удалить тип дня»);
  - настройка временных интервалов;
  - настройка ограничений записи;
  - заполнение расписания по периоду и дням недели;
  - каждая ветка заканчивается «Применить изменения».

**[Вывод]** Ветки «Регистрация» и «Авторизация» в OTP-модели сливаются в одну: регистрация происходит при первом успешном входе. Явный шаг «Продолжить работу? → Завершение» — артефакт формальной нотации, в web это просто закрытие вкладки.

## 8. Качество, сборка, эксплуатация

**[Факт]**
- Тестов нет: нет jest или vitest конфигов и файлов тестов.
- CI нет.
- Линтинг: `eslint-config-expo` и prettier только в `apps/native`; `knip` на корне; `turbo check-types`.
- Миграций нет: используется `db:push` без SQL-миграций, что недопустимо в production.
- Сервер слушает фиксированный порт 3000.
- Сборка сервера — `tsdown`, есть альтернативный `bun build --compile`.

## 10. Что сохранить и что пересмотреть

| Сохранить | Почему |
|---|---|
| Email OTP-вход без пароля | Работает, соответствует ожиданиям аудитории, нет хранения паролей |
| Модель «услуга: длительность + перерыв» | Ясная, покрывает основные кейсы |
| Шаблоны дня как единица планирования | Сильная идея: «как я обычно работаю» задаётся один раз |
| Правила заполнения: период, дни недели, смены 5/2 и 2/2 | Отражают реальные графики (смены — у мастеров в салонах, у инструкторов) |
| Горизонт записи (дни, дата, без ограничения) | Важен специалисту |
| Zod-схемы и сообщения на русском | Переносимы в web |
| PostgreSQL, Drizzle, Better Auth | Подходят и для web ([13](13-architecture-options.md)) |

| Пересмотреть | Почему → предложение |
|---|---|
| «Контакты» и поиск по username | Клиенту негде взять username, «заявки» не определены → **публичная ссылка** специалиста |
| Обязательная регистрация клиента | Барьер при первой записи → **гостевая запись с кодом** |
| Модалки поверх модалок | На web неудобно → отдельные страницы и боковые панели |
| Недельный список карточек с select | Медленно заполнять месяц → **месячная сетка и кисть** |
| Инструменты заполнения без предпросмотра | Риск испортить график → предпросмотр и подсчёт затронутых дней |
| Нижняя навигация с 3 вкладками | Мобильный паттерн → боковая навигация на desktop, нижняя на телефоне только в кабинете |
| Цвет события «сейчас» `#06cdec` и случайные градиенты | Нет системы → токены статусов ([09](09-design-specification.md)) |
