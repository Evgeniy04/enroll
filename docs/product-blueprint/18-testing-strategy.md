## 2. Ключевые тестовые наборы

### 2.1 Движок окон и расписания (unit, property-based)
- **TS-AVL-1:** окна не пересекаются друг с другом и с активными записями (с учётом перерыва).
- **TS-AVL-2:** каждое выданное окно принимается `createBooking` в той же модели (инвариант «окно ⇒ запись проходит»).
- **TS-AVL-3:** окна вне горизонта и раньше `now + min_notice` не выдаются.
- **TS-AVL-4:** часовые пояса `Europe/Kaliningrad`, `Europe/Moscow`, `Asia/Yekaterinburg`, `Asia/Vladivostok`, `Asia/Kamchatka`; клиент в другом поясе.
- **TS-TPL-1:** пересекающиеся блоки отклоняются; конец > 1440 отклоняется; итог шаблона считается правильно (с перерывом после последнего сеанса).
- **TS-RULE-1:** «Смены 2/2 со 2 по 30 ноября 2026 с якорем 2 ноября» → ровно 15 дат; «Пн–Пт октябрь 2026» → 22 даты; «Период 1–7» → 7 дат.
- **TS-RULE-2:** `fillEmpty` не трогает заполненные дни; `overwrite` заменяет их.
- **TS-SM-1:** все переходы машины состояний, запрещённые → ошибка.

### 2.2 Интеграционные
- **TI-BKG-1:** параллельные 50 вставок в одно окно → 1 успех, 49 × `slot_taken` (exclusion constraint).
- **TI-BKG-2:** просроченный hold не блокирует новую запись.
- **TI-BKG-3:** перенос атомарен — при конфликте старая запись не меняется.
- **TI-AUTH-1…4:** AUTH-01 AC1–AC4, включая проверку отсутствия кода в логах (перехват логгера).
- **TI-IDOR:** для каждого эндпоинта `/specialist/*` — запрос от специалиста B к ресурсу A → 404.
- **TI-NTF-1:** создание записи ставит ровно одну задачу каждого вида; повтор обработчика не шлёт дубль.
- **TI-MIG-1:** миграции применяются на пустую БД и на снапшот предыдущей версии; expand/contract-совместимость (старый код против новой схемы).
- **TI-RET-1:** задачи обезличивания удаляют ПД согласно [15](15-data-model.md) §6.
- **TI-SES-1:** выход удаляет cookie; отозванная сессия отклоняется на следующем запросе (AUTH-02).
- **TI-PRF-1:** при `booking_enabled = false` создание записи → 409 `booking_disabled`; EXIF удалён из аватара; старый slug отдаёт 301 (PRF-02).
- **TI-SVC-1:** архивированная услуга исчезает из окон, будущие записи сохраняются; удаление связанной услуги → 409 `service_in_use` (SVC-02).
- **TI-NTF-2:** напоминание ставится на `start − 24h` и не отправляется для отменённой записи (NTF-02).
- **TI-LOG-1:** логи, трассировки и `analytics_event` не содержат email, телефонов, имён, кодов и токенов (NFR-PRIV-02, LEG-03).

### 2.4 Производительность и нагрузка (k6)
- **TP-1:** 50 RPS смешанной нагрузки (70 % окна, 20 % профиль, 10 % записи) 15 мин: p95 в пределах NFR-PERF-02, ошибок < 0,1 %.
- **TP-2:** «Пик открытия записи» — 200 виртуальных пользователей атакуют 20 окон одного специалиста: 20 успешных записей, остальные 409, без 5xx.

### 2.5 Восстановление
- **TR-1:** ежеквартально — восстановление из бэкапа в изолированное окружение, проверка целостности (количество записей, ограничения), время ≤ RTO.

## 3. Связь тестов с требованиями
Полная матрица — в [23](23-traceability-matrix.md). Правило: у каждого AC требования MVP есть хотя бы один автоматизированный тест или явный ручной чек-лист.

## 4. Регрессия
- Каждый исправленный дефект получает тест.
- Ночной полный набор (E2E все браузеры, визуальная регрессия, Lighthouse).
- Перед релизом — полный набор и ручной аудит доступности на изменённых экранах.

## 5. Тестовые данные
Синтетические сиды (`pnpm db:seed`): 3 специалиста (маникюр в Москве, инструктор в Казани UTC+3, репетитор во Владивостоке UTC+10), услуги, шаблоны, месяц расписания, записи всех статусов. Реальные ПД в тестовых окружениях запрещены.

## 6. Ручное исследовательское тестирование
Перед пилотом — сессии по 60 мин по чартерам:
- «сломать расписание»;
- «запись из Telegram in-app»;
- «плохая сеть (3G, офлайн)»;
- «скринридер».

## 7. Классификация дефектов
- **S1:** потеря или утечка данных, двойная запись, невозможность записаться.
- **S2:** ключевой сценарий без обходного пути.
- **S3:** обходной путь есть.
- **S4:** косметика.

## 8. Критерии готовности MVP к выпуску (Definition of Done релиза)
1. Все AC требований с приоритетом MVP проходят автоматическими тестами или подписанным ручным чек-листом.
2. 0 открытых S1 и S2; S3 ≤ 10 с планом.
3. E2E-01…14 зелёные в Chromium, WebKit, Firefox.
4. axe: 0 нарушений уровня serious и critical. Ручной аудит UF-01, UF-04, UF-06, UF-07, UF-08 пройден.
5. NFR-PERF-01…03 в бюджете; TP-1, TP-2 пройдены.
6. ZAP baseline без High; зависимости без критических CVE; gitleaks чист.
7. TR-1 выполнен на staging.
8. Юридический минимум: политика, оферта, согласие опубликованы; уведомление РКН подано (если требуется); данные в РФ (§5.2 [17](17-security-and-compliance.md)).
9. Мониторинг и алерты настроены, дежурный контакт определён.
10. Название утверждено владельцем по итогам [12](12-naming-legal-review.md) — либо запуск под нейтральным техническим доменом без публичного продвижения.
