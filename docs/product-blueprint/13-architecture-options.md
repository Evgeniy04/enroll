**Принцип:** сначала требования, затем технологии. Существующий стек прототипа учитывается как *знание команды*, а не как обязательство.

**Ограничения владельца:** основная библиотека — **React**, язык — **TypeScript**.

## 2. Web-фреймворк

Версии на октябрь 2026 по открытым источникам ([приложение A](appendix-a-sources.md)):
- **TanStack Start** достиг 1.x в 2026 г.;

Методика: ✅✅ = 1,0, ✅ = 0,75, ⚠️ = 0,4, ❌ = 0 от веса. «SPA + API» набирает больше Next.js, но не выполняет AR-01 (обязательное требование), поэтому исключается независимо от суммы.

**[Решение D-08] TanStack Start.** Причины:
1. Продукт держится на состоянии в URL (вид календаря, дата, выбор окна). Типизированные search-параметры со схемой — его сильнейшее отличие.
2. Кабинет — клиентское приложение с кэшем данных. TanStack Query — естественная часть стека, без двух моделей кэширования.
3. Переносимость (Nitro, контейнер) — критична для российского хостинга (AR-08, AR-10).
4. Команда уже использует TanStack Form (прототип).

**Почему не ближайшие альтернативы:**
- **React Router 8** — самая сильная альтернатива и **запасной вариант**. Он уступает по типизации search-параметров. Миграция между ними умеренная: оба построены на Vite, домен и контракты фреймворк-независимы ([14](14-architecture.md) §2).
- **Next.js 16** не нужен: RSC и PPR не дают продукту существенной выгоды (публичных страниц немного, они простые), а модель кэширования и привязка оптимизаций к Vercel добавляют сложность и риск.
- **SPA + API** не обеспечивает AR-01 без дополнительной инфраструктуры.

**Риск выбора:** молодость TanStack Start (breaking changes в минорных версиях, меньше готовых решений). Митигация:
- фиксация версий;
- доменная логика в `packages/domain` без зависимостей от фреймворка;
- API на Hono (см. §3), не завязанный на server functions;
- триггер пересмотра — два блокирующих дефекта фреймворка за квартал.

## 3. Организация серверной части и API

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. REST `/api/v1` на Hono, смонтированный в catch-all server route Start** (один процесс) | Стабильный внешний контракт (бот, виджет, мобильное приложение), опыт команды с Hono, middleware (rate limit, CORS, логирование), OpenAPI-генерация из Zod | Два слоя маршрутизации |
| B. Только server functions Start | Минимум кода | Нет публичного контракта; привязка к фреймворку |
| C. tRPC | Типобезопасность | Не REST-контракт для внешних клиентов; ещё одна абстракция |
| D. GraphQL | Гибкие выборки | Избыточен для предметной области |
| E. Отдельный API-сервис | Независимое масштабирование | Два деплоя, CORS (AR-09) |

**[Решение D-09] Вариант A.**
- Браузер ходит в `/api/v1` через TanStack Query.
- SSR-загрузчики вызывают доменные сервисы напрямую (без HTTP), с теми же проверками доступа.
- Better Auth монтируется на `/api/auth/*`, как в прототипе.

Подробно — [19](19-infrastructure.md). Зарубежные PaaS (Vercel, Netlify, Fly.io, Render) **исключены** для ПД граждан РФ (ч. 5 ст. 18 152-ФЗ).

|---|---|---|---|---|
| Managed PostgreSQL | ✅ | ✅ | ✅ | ✅ |
| Контейнеры без управления серверами | ✅ Serverless Containers | ⚠️ Managed Kubernetes или VM | ⚠️ Apps или VM | ⚠️ |
| Почта (транзакционная) | ✅ Postbox | ❌ сторонний | ❌ сторонний | ❌ |
| Секреты | ✅ Lockbox | ⚠️ | ⚠️ | ✅ |
| 152-ФЗ (заявлено провайдером) | ✅ | ✅ (до УЗ-1) | ✅ | ✅ |
| Стоимость MVP | Средняя | Средняя | **Низкая** | Средняя |
| Переносимость | Контейнер и PG — да | Да | Да | Да |

**[Решение D-16] Yandex Cloud** — для MVP:
- больше управляемых сервисов при минимальной эксплуатации (контейнеры, PG, почта, секреты, логи);
- запасной вариант — Selectel (сертификация, независимость);
- бюджетный вариант для пилота — Timeweb Cloud VM с Docker Compose.

Архитектура не использует проприетарные API, кроме S3-совместимых хранилища и почты.
