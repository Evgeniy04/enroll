## 2. Web-фреймворк

Версии на октябрь 2026 по открытым источникам ([приложение A](appendix-a-sources.md)):
- **Next.js 16** вышел 21.10.2025;
- **TanStack Start** достиг 1.x в 2026 г.;
- **React Router 8** вышел 17.06.2026.

**Перед стартом реализации версии нужно перепроверить по официальной документации.**

### 2.1 Сравнение по частям продукта

| Часть продукта | TanStack Start 1.x | Next.js 16 (App Router) | Кто выигрывает |
|---|---|---|---|
| Публичная страница `/{slug}` (часто открывается из Telegram/VK in-app на слабом телефоне) | SSR; клиенту уходит JS всего маршрута для гидрации | Server Components: статичные части профиля не попадают в клиентский JS; Metadata API для Open Graph | **Next.js**, заметно |
| Выбор времени `/{slug}/book?service=&date=&time=` | Типизированные search-параметры со схемой | `searchParams` — строки; разбор через nuqs с парсерами Zod | Start |
| Календарь `/app/calendar?view=&date=` (кэш между неделями, фоновое обновление) | Загрузчики + TanStack Query — одна модель данных | Клиентский компонент + TanStack Query (см. D-31) | Start, небольшое преимущество |
| Расписание «кистью» (массовые мелкие изменения, «Вернуть») | Мутации Query с откатом | То же на клиенте (TanStack Query) | Равно при D-31 |
| Граница сервер/клиент | Нет директив | `"use client"` — дисциплина, но и выигрыш в JS на публичных страницах | Зависит от экрана |
| API для кабинета, бота и виджета | oRPC или Hono в server route | oRPC или Hono в Route Handler | Равно |
| Better Auth | Официальная интеграция | Официальная, более обкатанная | Next.js, немного |
| Хостинг в РФ (контейнер) | Nitro, обычный Node-контейнер | `output: "standalone"`; при нескольких инстансах кэш страниц требует своего cache handler — в MVP не используем ISR (D-32) | Start, немного |
| Инструменты | Vite, общий конфиг с Vitest | Turbopack, отдельная настройка Vitest | Start, немного |
| Зрелость, документация, ответы на вопросы | Молодой (1.x в 2026) | Очень зрелый; модель кэширования менялась между 13–16 | **Next.js** |
| Экосистема и найм в РФ | Меньше в разы | Крупнейшая | **Next.js**, заметно |

### 2.2 Решение

**[Решение D-08, пересмотрено 11.10.2026 по решению владельца] Next.js 16 (App Router).** Причины:
1. Зрелость, документация и экосистема снижают риск для небольшой команды; проще найм.
2. Server Components дают минимальный JS на публичных страницах, куда клиенты приходят из встроенных браузеров соцсетей.
3. Сильные стороны TanStack Start (типизированный URL, единая модель данных) достижимы в Next.js библиотеками nuqs и TanStack Query ценой дополнительных зависимостей.

Отказ от альтернатив:
- **TanStack Start** — технически лучше подходит для кабинета, но молодость фреймворка и меньшая экосистема перевешивают по решению владельца. Остаётся запасным вариантом; домен и API от фреймворка не зависят.
- **React Router 8** — зрелый, но экосистема меньше, чем у Next.js, а преимущества перед Start по типизации URL нет.
- **SPA + API** — не выполняет AR-01.

### 2.3 Правила использования Next.js в проекте

| Правило | Почему |
|---|---|
| Публичные страницы (P-01, P-10, P-40) — Server Components; интерактивные острова (лента дней, окна, форма) — клиентские компоненты | Минимум JS |
| Кабинет `/app/*` — клиентские компоненты с TanStack Query поверх `/api/v1` (D-31) | Оптимистичные обновления, кэш, один контракт |
| **Server Actions не используются** для доменных операций; все изменения идут через `/api/v1` | Один контракт для веба, бота и виджета; единые проверки и rate limit (D-09) |
| Состояние в URL — nuqs с парсерами Zod из `contracts` | Типизированный URL (AR-03) |
| Проверка сессии — в серверных layout `/app` и `/me` (`redirect` на `/login?returnTo=`); `middleware` только для быстрой проверки наличия cookie | Middleware не заменяет авторизацию |
| Без ISR и `unstable_cache` для данных записи в MVP; публичный профиль — динамический рендер + заголовки CDN `s-maxage=60` (D-32) | Предсказуемый кэш при нескольких инстансах |
| `output: "standalone"`, Docker; `next/image` с локальной оптимизацией (sharp) или отключён для аватаров (уже оптимизированы при загрузке) | Хостинг в РФ без Vercel |
| Шрифты — `next/font/local` (self-host) | Без передачи IP третьим лицам (D-23) |
| Телеметрия Next.js отключена (`NEXT_TELEMETRY_DISABLED=1`) | Минимизация внешних передач |

**Риск выбора:** изменения модели кэширования и API между мажорными версиями. Митигация: не использовать экспериментальные возможности, обновлять мажорные версии осознанно (раз в год, отдельной задачей), домен и API — вне фреймворка.

## 3. Организация серверной части и API

Потребители API: собственный кабинет (основной объём), Server Components (на сервере, без HTTP), Telegram-бот (в том же монорепозитории — вызывает use cases напрямую), будущие виджет и мобильное приложение (нужен публичный HTTP-контракт только для записи клиента).

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. oRPC в Route Handler Next.js** | Процедуры описываются один раз схемами Zod; RPC-клиент с типами и готовыми `queryOptions`/`mutationOptions` для TanStack Query; та же процедура публикуется как REST с OpenAPI 3.1; серверный клиент для Server Components с тем же контекстом | Моложе tRPC; лимиты частоты — собственный middleware |
| B. Hono + `@hono/zod-openapi` | Зрелый HTTP-фреймворк, богатые middleware, опыт команды | Типизация в браузере через клиент Hono (тяжело для TypeScript на больших API) или генерацию; больше ручной работы для TanStack Query |
| C. tRPC v11 | Самый зрелый RPC для Next.js, глубокая интеграция с TanStack Query | OpenAPI только через сторонний адаптер |
| D. Server Actions | Минимум кода | Нет публичного контракта, только POST, второй путь изменения данных в обход общих проверок |
| E. Отдельный API-сервис | Независимое масштабирование | Два деплоя, CORS (AR-09) |

**[Решение D-09, обновлено 11.10.2026] Вариант A — oRPC.**
- Один роутер процедур в `packages/api`; подключается в Next.js двумя обработчиками из одного файла маршрута: RPC (`/api/rpc/*`) для собственного фронтенда и OpenAPI (`/api/v1/*`) для публичной части.
- OpenAPI-документ публикуется только для публичных процедур (`/api/v1/public/*`, документ [16](16-api-specification.md) §4); процедуры кабинета — внутренний контракт.
- Server Components вызывают процедуры серверным клиентом oRPC (без HTTP) — с теми же проверками доступа.
- Server Actions для доменных операций не используются.
- Запасной вариант — tRPC + отдельные Route Handlers для публичной части; use cases от транспорта не зависят.

## 5. Аутентификация и сессии

| Вариант | Email OTP | Сессии в БД | Drizzle | Вывод |
|---|---|---|---|---|
| **Better Auth 1.x** | ✅ плагин (работал в прототипе) | ✅ | ✅ адаптер | **Выбран владельцем (D-13)** |
| Собственный модуль (руководство Lucia) | ✅ | ✅ | ✅ | Запасной вариант |
| Auth.js | ⚠️ magic link, OTP вручную | ✅ | ✅ | — |
| Облачные сервисы (Clerk, Auth0, WorkOS) | ✅ | — | — | Исключены: данные пользователей за рубежом (152-ФЗ) |

Условия использования Better Auth (с учётом проблем, с которыми владелец сталкивался в феврале 2026 г.):
- версия фиксируется точно (без `^`), обновления — отдельной задачей после чтения changelog и Security Advisories;
- конфигурация: `sameSite: "lax"`, cookie с префиксом `__Host-`, без `expo()` и `exp://`, плагин `phoneNumber` отключён до появления SMS-провайдера, хранение лимитов в БД (несколько инстансов), отправка писем через очередь (без логирования кодов);
- Better Auth монтируется в Route Handler `app/api/auth/[...all]`; middleware oRPC получает сессию через серверный API Better Auth и кладёт `actor` в контекст;
- подтверждение записи гостя (hold) — процедура oRPC, которая в одной транзакции проверяет код через серверный API Better Auth, подтверждает hold и создаёт сессию; точные вызовы проверяются на spike;
- набор тестов TI-AUTH-1…4 и TI-SES-1 ([18](18-testing-strategy.md)) запускается при каждом обновлении версии;
- **триггер перехода на собственный модуль:** блокирующий дефект без исправления > 2 недель или невозможность реализовать подтверждение hold штатными средствами.
